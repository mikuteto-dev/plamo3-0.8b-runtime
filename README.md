# PLaMo 0.8B 専用ランタイム

`pfnet/plamo-3-translate-0.8b` のBF16重みをそのまま使う、Swift＋Metal製の翻訳CLI。
M2 MacBook Air、GPU 8コア、メモリ16GBで検証済み。
推論時にPython、PyTorch、MLX、llama.cppを使わない。

## 実行

Xcodeの開発環境と、モデル取得用のPython 3.11以降が必要。

```sh
python3 scripts/download.py
swift build -c release
.build/release/plamo --to en '会議は来週の月曜日に変更されました。'
```

```text
The meeting has been rescheduled for next Monday.
```

`scripts/download.py` は元語彙を変更せず、任意の検索木キャッシュ `tokenizer.jsonl.trie` も準備する。
既存環境は同じコマンドを再実行する。元語彙とキャッシュのSHA-256が一致するときだけ利用し、不一致や欠落時は元語彙を読む。
旧 `tokenizer.jsonl.batch` は使わず、自動削除もしない。新キャッシュがない場合、旧グループ化版より起動が遅くなることがある。
キャッシュは約5.34MBのディスク領域を追加するが、推論時のPython依存はない。

可逆圧縮モードも利用できる。
以下の変換には検証環境のNumPyが必要だが、推論時のPython依存はない。

```sh
.venv/bin/python scripts/pack_weights.py
.build/release/plamo --packed --to en '会議は来週の月曜日に変更されました。'
```

BF16の全ビットを保持し、Metalで読み出すときだけ復元する。
通常モードを既定とし、圧縮モードは `--packed` で明示的に選ぶ。
圧縮キャッシュはv2形式に更新したため、旧 `model.p12` がある場合も上のコマンドで再生成する。
元のBF16重みは変更しない。

本文を引数で渡さなければ、標準入力からUTF-8で読む。
翻訳は標準出力、計測値のJSONは標準エラーに出力する。

```sh
printf '%s' 'This system is convenient.' | .build/release/plamo --to ja
.build/release/plamo --to en --max-tokens 128 --repeat 5 '会議は来週の月曜日に変更されました。'
```

- `--to`：翻訳先。既定は `ja`。モデルの53言語コードを受け付けるが、翻訳品質の確認は日英のみ。
- `--max-tokens`：出力上限。分割時は区間ごとに適用する。既定は256。JSONの `stop_reason: "length"` は上限到達による打ち切り。
- `--context`：入出力合計の上限。省略時は入力トークン数（分割時は最長区間）＋出力上限に合わせて確保する。最大32,768。
- `--model`：モデル格納先。既定は `models/plamo`。
- `--repeat`：同一モデルを保持して繰り返し計測する回数。
- `--stream`：生成したトークンをデコードしながら標準出力へ逐次書き出す。末尾の改行は追加しない。
- `--segment-tokens N`：区間ごとの入力上限（プロンプトとBOSを含む64〜8,192トークン）。省略時は分割しない。
- `--batch4`：最大4区間をGPUでまとめて生成する実験機能。`--segment-tokens` が必須で、既定は無効。
- `--repetition-penalty F`：文脈に既にあるトークンのlogitをFで割る（既定1で無効）。
- `--frequency-penalty F`：文脈での出現回数に比例してlogitを引く（既定0で無効）。
- `--no-repeat-ngram N`：文脈に既にあるn-gramを完成させるトークンを禁止する（既定0で無効）。
- `--loop-limit N`：末尾が同じブロックをN回以上反復したら `stop_reason: "repeat"` で打ち切る（既定0で無効）。

`--stream` は途中まで不完全なUTF-8バイト列を保留し、文字が完成した時点で書き出す。
分割しない場合、出力した文字を連結すると、同じ生成IDの `decode` と一致する。
計測値のJSONは従来どおり標準エラーにのみ出力する。

反復制御は既定で無効とし、元のgreedy実装と同じ出力を保つ。
`--repetition-penalty` と `--frequency-penalty` はCPUでlogitを調整してargmaxし直す。
`--no-repeat-ngram` はハード制約なので通常の文でも反復4-gramを禁じる点に注意する。
`--loop-limit` は反復制御ではなく、品質を変えずに暴走を短く切るための安全弁である。

原文にPLaMoの予約区切り文字が含まれる場合は拒否する。
会話履歴、用語集、文体指定、複数リクエストの並列翻訳は実装していない。
ローカルHTTPサーバーは下記の翻訳ページで使用する。

## 区間分割

複数文書や長文は、次のように分割して翻訳できる。

```sh
.build/release/plamo --packed --stream --segment-tokens 512 --max-tokens 2048 --to en < documents.txt
```

改行ごとに区切り、長い行は文末、空白、Unicode文字境界の順で区切る。
各区間の実トークン数を検査し、モデルと重みは1回だけ読み込む。
CLIの既定では区間ごとにKVキャッシュと生成履歴をリセットして順番に翻訳するため、前の文書を次の文書の文脈へ混ぜない。
文書の意味的な境界を自動判定するものではないため、文書間には改行を入れる。

区間間の原文の空白と改行は保持する。
空白のない位置で分割した場合は、訳文同士がつながらないよう改行を追加する。
`--max-tokens` は区間ごとの出力上限、`--context` は区間ごとの入出力合計上限になる。
途中の区間が上限や反復検出で打ち切られた場合は、その場で全体の処理も止め、残りを飛ばして完了扱いにはしない。

JSONの各runには、区間ごとの `segments`、予定数の `segments_total`、EOSまで完了した数の `segments_completed` を追加する。
合計の `output_ids` は区間の生成IDだけを連結したもので、コピーした空白と追加した改行は含まない。
検証用の `--tokens`、`--tokenize`、`--decode`、`--dump-logits` とは併用できない。
1文字だけで入力上限を超える場合も、文字を壊さずエラーにする。

前の区間の文脈を引き継がないため、代名詞や用語、文体の一貫性が落ちる可能性がある。
分割は完訳や翻訳品質を保証するものではなく、全文翻訳を2〜3秒にする機能でもない。
分割と実エンジンの回帰試験は `PLAMO_SEGMENTS=1 swift test -c release --filter SegmentTests` で実行する（先に `swift build -c release` が必要）。

### 実験用の4区間バッチ

`--batch4` は同じ重みを共有し、区間ごとのKVと位置を分離して最大4区間をまとめて生成する。
入力処理は区間ごとの順次実行のままで、訳文は原文の区間順にストリーム出力する。
入力が1区間だけなら通常経路を使い、バッチ用のKVと作業領域は確保しない。
途中の区間が出力上限に達したら、先に生成していた後続区間も出力せず、全体を止める。

通常の実行バイナリを置き換えずに試すには、候補用のビルド先を使う。

```sh
swift build -c release --scratch-path results/experiments/batch-cli-build
results/experiments/batch-cli-build/release/plamo --packed --stream --segment-tokens 512 --batch4 --max-tokens 2048 --to en < documents.txt
```

通常BF16と可逆圧縮に対応するが、greedy生成専用で、`--context` は8,192未満に限る。
QSA、MTP、反復制御とは併用できない。
複数区間では重みを複製しないが、追加KVと作業領域を確保するため、省メモリ機能ではない。
JSONの `batch4` は指定状態を示し、単一区間でも `true` になる。
実際に入力処理した `prefilled_input_tokens`、打ち切りで破棄した `discarded_output_tokens` も記録する。

3,203文字の1例は起動から終了まで13.75秒から6.05秒になり、訳文と全生成IDが逐次版と一致した。
同じ800文字の原文を4回並べた入力で各方式1回ずつの観測であり、一般的な改善率や12,000文字の結果ではない。
条件と検証手順は [BENCHMARK.md](BENCHMARK.md#文書順の出力と実験用cli) に記載。
12,000文字の追加比較と単一区間の確保量削減は [BENCHMARK.md](BENCHMARK.md#12000文字の区間バッチ生成) を参照。
翻訳ページではこの4区間処理を有効にしている。
ページ側の実測と、初回表示や確保量の増加は [BENCHMARK.md](BENCHMARK.md#翻訳ページでの4区間適用) を参照。

## ブラウザーで試す

モデルと可逆圧縮ファイル `models/plamo/model.p12` を準備した後、Bunで起動する。

```sh
bun run web
```

`http://127.0.0.1:3000` を開くと、日本語と英語を翻訳できる。
ポートを変える場合は `PORT=3001 bun run web` とする。
デジタル庁デザインシステムの公式HTML/CSSを使い、出典とMITライセンスは `web/vendor/dads/` に同梱した。
アプリの実行時依存パッケージはなく、外部フォント、CDN、外部翻訳APIを呼び出さない。

サーバーは `127.0.0.1` のみで待ち受け、同一オリジンからの翻訳だけを受け付ける。
原文と訳文をファイルやアクセスログへ保存しない。
翻訳ごとに既存CLIを標準入力で呼び出し、完了または中止後にモデルを解放する。
可逆圧縮を使用し、QSAとMTPは無効にしている。

同時実行は1件までで、別のタブから実行中の翻訳があればエラーを表示する。
原文は12,000 UTF-16コード単位以内、リクエストは64KiB以内、区間ごとの出力は2,048トークンまで、全体の実行は180秒までとする。
モデル自身の入出力合計32,768トークンの上限は区間ごとに適用する。
サーバーは `--stream --segment-tokens 512 --batch4` でCLIを起動し、生成された文字を原文順のNDJSONで配信する。
複数区間では最大4区間をまとめ、単一区間では追加バッファを作らない通常経路を使う。
複数区間の完了時間の短縮を優先する一方、最初の表示までの時間やMetal確保量は増える場合がある。
ページ側は届いた文字をアニメーションで表示し、出力上限による打ち切りは警告する。
中止や切断時はサーバーがCLIプロセスを終了する。
生成はgreedyのままにし、原文にある意図的な繰り返しを罰しない。
以前の自動 `--repetition-penalty 1.1 --loop-limit 4` は使用せず、文書間の混入は区間分割で避ける。
区間内での反復は起こり得るため、出力上限は維持する。

```sh
bun run test:web
# ブラウザーテストの開発依存をインストールする。
bun install
bun run test:browser
```

ブラウザーテストはインストール済みのGoogle Chromeを使い、日英の実推論、コピー、中止、画面幅、エラー表示を検証する。
別のChromium系ブラウザーを使う場合は `CHROME_PATH` に実行ファイルを指定する。

## 長文の制限

分割しない場合、最大32,768トークンは入力と出力の合計で、32,768トークンの原文に訳文の余地を追加できるわけではない。
合成列32,768トークンの全入力処理と数値照合は成功したが、最大長近くの自然文を完訳できたという結果ではない。

分割せずに公開WMT24++の37文書を連結した入力14,435トークンを処理した場合は、出力約3,917トークン目から同じ句を反復し、上限18,333トークンまでEOSが出なかった。
打ち切りまで約379秒、chrFは15.61で、この条件の全文翻訳は失敗した。
単一の長文書ではなく、ニュースとSNSを連結した1例である。
条件と参照実装による切り分けは [BENCHMARK.md](BENCHMARK.md#長い自然文の全文生成) に記載。

`--segment-tokens 512` で同じ原文を再実行すると、413区間すべてがEOSまで終了し、chrFは48.87だった。
ただし順次処理で約789.6秒を要し、高速化の達成とは扱わない。
条件と検証範囲は [BENCHMARK.md](BENCHMARK.md#区間ごとの順次翻訳) に記載。

## QSAとMTPの実験

学習済みの追加重みを使う `--qsa` と `--mtp` を実装した。
どちらも既定では無効で、通常の逐次生成に対する一貫した高速化や省メモリ化は確認できていない。
元のBF16重みは変更せず、追加重みもBF16で保存する。

```sh
# 後述の検証環境を準備してから実行する。特徴収集と学習にはPythonとMLXが必要。
.venv/bin/python scripts/train_auxiliary.py --collect --train-sentences 256 --valid-sentences 64 --mtp-steps 512

.build/release/plamo --packed --qsa --to ja < input.txt
.build/release/plamo --packed --mtp --to ja < input.txt
.build/release/plamo --packed --qsa --mtp --to ja < input.txt
```

- `--qsa`：大域Attentionの2層で、学習済みの4ヘッド選択器が4トークン単位のブロックを選ぶ。既定の予算は2,048トークンで、未完了の末尾を最大3トークン追加する。
- `--qsa-budget N`：予算を4以上2,048以下の4の倍数に変更する。QSAも有効になる。
- `--mtp`：確定済みの次トークンに続く1候補を提案し、この2位置を元モデルで一括検証する。不一致の候補は棄却する。

QSAは選択器だけを蒸留した試作で、疎なAttentionに合わせた本体の追加学習は未実施。
KV履歴は削除せず、選択器の履歴と作業領域が増える。
MTPはQwenの予測器そのものではなく、ランク256の残差MLPによる先読み。
学習済みの2ヘッドのうち第1だけを実行し、重みの再学習や変換は不要。
棄却時の巻き戻しと、局所RoPEの逐次計算と同じ順序を使う2位置専用カーネルを実装した。

導入時の測定では長文のQSAが146.84秒から156.80秒、短文のMTPが16.36秒から19.24秒になった。
測定の変動が大きく、この数値を一般的な性能差とは扱わない。
条件、受理率、メモリ、品質の限定は [RESEARCH.md](RESEARCH.md#qsaとmtpの実装結果) に記載。

```sh
.venv/bin/python -m unittest discover -s scripts -p test_auxiliary.py
PLAMO_LONG_TEST=1 swift test -c release --filter VerificationTests
```

追加重みは `models/plamo/auxiliary.safetensors`、学習結果は `models/plamo/auxiliary.json` に保存する。
学習データはOPUS配布のTatoeba日英対訳（CC BY 2.0 FR）。
取得したライセンスは `results/data/Tatoeba-LICENSE.txt` に保存する。
追加重みを配布する際も、元モデルとデータのライセンス条件の確認が必要。

## 専用化した部分

**重みを複製しない。**
通常モードは元のsafetensorsを読み取り専用でメモリマップし、Metalの共有バッファから直接参照する。
圧縮モードは別ファイル `model.p12` を作成して直接参照し、元の重みを変更しない。
どちらも重み全体のFP32変換やGPU転送用コピーを行わない。

**入力埋め込みをGPUに置かない。**
入力埋め込みと出力ヘッドは別の重みなので、約330MBの入力埋め込みをGPUのマッピング範囲から外せる。
入力で使う行だけCPUで読み、少量の活性値としてGPUへ渡す。
入力埋め込みのファイル領域自体はCPUからマップしたままで、OSの再利用可能なファイルキャッシュに残る場合がある。

**演算をこの形状に固定する。**
生成時はBF16の4要素ベクトル読み込みと32レーンの行列ベクトル積を使う。
入力処理は16トークンずつのSIMD-groupタイル行列積にする。
中間バッファを全層で再利用し、出力ヘッドは最後の入力位置だけ計算する。
行列積の重み復元を4要素単位にまとめ、連続する正規化を統合してGPU呼び出しを減らす。
Attentionスコア領域は必要な分だけ拡張し、入力処理後は生成に必要な行数まで戻す。

**KVキャッシュをモデルの窓幅に合わせる。**
14層は直近2,048トークンのリングバッファ、残り2層は全履歴を保持する。
キャッシュはBF16のまま。
局所Attentionでは未回転のキーを保存し、公式HF実装の切り詰め後の座標でRoPEを適用する。

重みとKVキャッシュの量子化は行わない。
一時活性値はFP32領域に置き、元のBF16演算境界で丸める。
演算順序が異なるため、公式実装とのビット単位の一致は保証しない。

## 実測

800文字の公開ニュース入力をEOSまで翻訳すると、初回を除く2回の中央値は英→日3.27秒、日→英7.00秒だった。
出力はそれぞれ180トークンと368トークンで、モデル初期化を含まない。
別の12,000文字入力では、訳文生成を除いた入力処理だけでも2回目に英→日4.78秒、日→英13.06秒を要した。
出力上限を8,192トークンにした別のCLI試験では、同じ12,000文字からのEOS到達まで英→日58.80秒、日→英185.95秒だった。
訳抜けなどの品質は未検証で、EOS到達を完訳の証明とは扱わない。
測定後にはバッテリー駆動で低電力モードが有効だったため、AC電源での比較も未確認である。
12,000文字を2〜3秒で完了する目標は未達で、64位置の投影処理案も速度改善を確認できず採用していない。
詳細は [BENCHMARK.md](BENCHMARK.md#800文字と12000文字のレイテンシ調査) に記載。

検証済みキャッシュのUTF-8を直接連結し、IDからの文字列復元を高速化した。
初期化を除いたデコード単体は3回の比較で約1.7〜2.3倍となり、32,768 IDでは最終比較で4.54→2.00msだった。
全107,520語のUTF-8が元JSONL経路と一致し、不正なUTF-8の置換とトークンをまたぐ有効な列も検証した。
訳文生成全体の約2倍速や、プロセス全体の一律の高速化を示す値ではない。
詳細は [BENCHMARK.md](BENCHMARK.md#デコード時のutf-8直接連結) に記載。

トークナイズの累積コスト配列を循環配列にし、標準語彙では入力長によらず最大512バイトにした。
32,768トークンになる英語入力で、ホスト側ピークRSSを3回の比較で約1.28〜1.33MB減らし、公式参照と全IDが一致した。
短い入力のプロセス全体の省メモリ化や一律の高速化を示す結果ではない。
詳細は [BENCHMARK.md](BENCHMARK.md#トークナイズの累積コスト配列) に記載。

トークナイズの分割長配列を32bitにし、32,768トークンになる英語入力でホスト側ピークRSSを3回の比較で約0.62〜0.68MB減らした。
スコアの64bit精度と出力IDは維持し、入力全体の長さは制限していない。65,537文字の単一トークンも検証した。
これは長文エンコード中の一時領域の削減で、短文翻訳の常駐メモリやGPU生成を改善した値ではない。
詳細は [BENCHMARK.md](BENCHMARK.md#トークナイズの分割長配列) に記載。

キャッシュ内の語彙文字列を必要なIDだけ復元する方式にし、短文翻訳CLIのホスト側ピークRSSを3回の比較で約1.25〜1.27MB減らした。
最終比較は50.282→49.013MBで、Metal割当と訳文・生成トークン列は変更前と一致した。
トークナイズ単体のCLIは約11〜20%短縮したが、翻訳全体の時間は変動しており、一律の高速化や速度維持を保証する結果ではない。
元語彙のJSONLへ戻る経路、キャッシュ検証、キャッシュ形式は維持し、再生成も不要である。
詳細は [BENCHMARK.md](BENCHMARK.md#語彙文字列の遅延復元) に記載。

## 検証

`models/`、`results/`、ビルド成果物とローカル環境はリポジトリに含めない。
モデルは上記の取得手順で用意する。
`BENCHMARK.md` の `results/experiments/` は当時のローカル実験を指し、実験用ソースや計測データも非同梱である。

```sh
mkdir -p results
swift test -c release

# 参照実装は検証時だけ使用する。
python3 scripts/download.py --reference
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements-verify.txt
.venv/bin/python scripts/verify.py
.venv/bin/python scripts/verify_long.py
.venv/bin/python scripts/bench.py
.venv/bin/python scripts/pack_weights.py
.venv/bin/python scripts/verify.py --packed
.venv/bin/python scripts/verify_long.py --packed

# 最大長の全入力を処理する。合成列による数値検証で、全文翻訳の品質試験ではない。
.venv/bin/python scripts/verify_long.py --packed --lengths 32768
.venv/bin/python scripts/verify_long.py --lengths 32768 --reuse-reference
PLAMO_MAX_TEST=1 swift test -c release --filter 'MaximumTests.testMaximumContextAndDecode|VerificationTests.testMaximumPair'

.venv/bin/python scripts/bench_document.py --label packed --packed --repeat 3

# この端末で行列ベクトル積のレーン幅を比較する。
PLAMO_TUNE=1 swift test -c release --filter TuningTests
```

確認済みの範囲：

- トークナイザー44例が公式実装と一致。
- 短文5例で次トークンが一致。logitsのRMSEは約0.028〜0.077。
- 日英翻訳3例でMLX参照実装と生成トークン列が一致。
- 2,049と4,097トークンの入力でHF方式のキャッシュ参照計算と次トークンが一致。
- リングバッファの折り返し、因果マスク、窓幅、行列の端数、入力エラー、壊れた重みヘッダーを単体テスト。

32,768トークンについては合成入力の全位置を処理し、参照logitsと照合した。
`--tokens` と `--dump-logits` を併用する検証時だけ `--max-tokens 0` を指定できる。
最大長近くの自然文生成は上記の連結入力で失敗した。一般的な長文品質、長時間の連続負荷、消費電力、M2以外のGPUは未検証。
